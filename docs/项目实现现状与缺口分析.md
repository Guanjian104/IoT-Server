# 项目实现现状与缺口分析

## 1. 分析范围与结论

- 分析日期：2026-11-15。
- 分析对象：当前仓库的 Go 源码、SQL 迁移、配置、脚本、测试及实施文档。

- 本文是分析时点的代码与验证快照，不是修复完成记录，不替代人工验收，也不改变既有阶段结论。

**总体定位：项目已经实现本地 MQTT 设备业务闭环，以及使用测试替身的 RTC 控制平面；尚未实现真实音视频业务和完整生产交付。**

### 2.2 用户、权限与设备管理

- 用户以用户名和密码登录，密码使用 bcrypt；访问令牌由服务端生成，数据库保存摘要和有效期。
- 后续请求通过 Bearer Token 取得当前身份，不信任请求体自行声明的用户 ID。
- 支持平台管理员和设备级 `manage`、`view`、`call`、`ticket` 授权。
- 支持设备登记、列表、能力与当前属性查询，以及授权、启用、禁用和吊销接入资格。
- 登录和命令创建使用 Redis 限流；Redis 失败时拒绝相关操作。
- 已有部分审计记录，但不是覆盖所有状态变化的完整审计系统。

主要代码：`internal/api/httpapi/server.go`、`internal/store/users.go`、`internal/store/devices.go`。

### 2.3 MQTT 设备业务

| 能力 | 已有行为 |
|---|---|
| 接入认证 | Hook 校验共享设备口令、合法 ClientID、设备登记、启用和吊销状态 |
| Topic ACL | 设备只能发布自己的 report、set_reply、status，并订阅自己的 property/set；拒绝越权和通配访问 |
| 禁用踢线 | 更新数据库后调用 EMQX 管理 API 尝试断开设备 |
| 属性上报 | 校验协议、功能点与类型，写当前属性和历史 |
| 去重 | 按租户、设备、msgId 和原始载荷摘要去重；同 msgId 的不同载荷保留 |
| 异步命令 | 命令先入库，后台领取后发布，支持回执和超时等状态 |
| 会话在线 | 消费 EMQX 系统连接事件，区分 MQTT 在线和设备自报状态，过滤部分旧会话断线事件 |
| 短时数据库故障 | 已进入当前进程的消息在内存队列中重试，持久化成功后再 ACK |
| 多实例基础 | 共享订阅与数据库任务领取，具有本地双实例测试用例 |

主要代码：`internal/bridge/`、`internal/mqttmsg/`、`internal/presence/`、`internal/store/commands.go`、`internal/store/messages.go`。

当前协议面向已有中控固件，功能点包括温湿度和六路布尔开关，不是通用设备协议引擎。命令的 accepted 表示收到设备成功回执，不等于已经独立核验物理状态达到目标值。

## 4. 尚未形成的完整业务

### 4.1 真实视频观看

仍需设备视频采集和编码、实际发布能力、真实流控制协议、正式媒体服务、可连接媒体凭证、播放客户端及首帧和失败反馈。

目前没有证据表明这些已经接通。现有控制事件把会话推进到 ACTIVE，不能替代真实可播放验证。

### 4.2 真实双向通话

仍需设备音频硬件和软件能力、被叫与邀请协议、双方媒体身份与凭证、双向收发、音频路由、建连超时、断线重连、挂断清理及私有轨道隔离。

普通 Viewer 不得订阅通话 APP 的私有上行，这需要真实 Provider 的权限能力和端到端负向测试，而非仅靠业务角色名称。

### 4.3 网络、客户端与生产环境

- 未完成目标家庭网络、移动网络、网络切换和强制 TURN 验证。
- 仓库没有完整 APP 或 Web 管理端；如目标包括完整产品，需要独立交付客户端工程。
- 当前依赖配置限制在本地，并固定部分账号、库名和管理端口，不是替换环境变量即可投入生产。见 `internal/config/deps.go:85`、`:174`。
- 尚缺生产拓扑、高可用、TLS、内部接口隔离、密钥轮换、容量长稳、故障恢复、备份恢复、监控告警及灰度交付实证。
- 文档中的 10,000 台设备是容量目标，不是当前已经证明的承载能力，也不等于同数量的视频能力。

## 5. 已有实现的正确性与可靠性风险

以下为静态代码核对结果，未逐项进行故障复现。优先级表示建议修复顺序，不表示已完成修复或已出现生产事故。

### 5.1 设备与 MQTT

| 编号 | 优先级 | 问题与影响 | 代码依据 |
|---|---|---|---|
| M01 | 高 | sending 且 attempts 小于 3、截止时间已过的命令，不满足重排、人工处理或超时 SQL 条件，可能永久卡住 | `internal/store/commands.go:192` |
| M02 | 高 | 一批最多 8 条发送共用 4 秒上下文，每条可等待 3 秒；慢 Broker 下结果落库可能失败，并存在过期后继续发送窗口 | `internal/bridge/bridge.go:252` |
| M03 | 高 | 禁用/吊销只在入口阻止新命令，已排队命令缺少领取或发送前复核和取消策略 | `internal/api/httpapi/server.go:236`、`internal/store/commands.go:74` |
| M04 | 中高 | uncertain 缺少自动核对和人工恢复 API，后续成功回执也不能直接使其收敛 | `internal/store/commands.go:132`、`:148`、`:192` |
| M05 | 中高 | 入站只有内存队列且使用 Clean Session，不能承诺崩溃、断连和离线期间不丢消息 | `internal/bridge/bridge.go:41`、`internal/bridge/inbound.go` |
| M06 | 中高 | 队列没有明确容量限制和毒消息隔离，持续失败可能导致内存增长或队头阻塞 | `internal/bridge/inbound.go:21`、`:89` |
| M07 | 中 | 当前属性按处理顺序覆盖，旧时间报文可能覆盖新值；在线状态缺少周期校准和完整重复事件处理 | `internal/store/messages.go:42`、`internal/presence/presence.go` |
| M08 | 中 | 共享口令不能提供物理设备之间的独立身份隔离；服务账号具有全设备发布能力 | `internal/api/httpapi/mqtt.go`、`internal/mqttmsg/access.go` |
| M09 | 中 | 同设备命令缺少严格串行执行和设备侧幂等实证，QoS 1 不代表 exactly-once | `internal/store/commands.go:74`、`internal/bridge/bridge.go:280` |
| M10 | 中 | 订阅完成状态、踢线最终结果和异常命令积压未形成完整就绪与运维闭环 | `internal/bridge/bridge.go:81`、`internal/api/httpapi/server.go:403` |

还需核验 Redis 限流 INCR/EXPIRE 的原子性、用户名大小写与限流键的一致性、重复启停操作的幂等响应，以及各类历史数据增长边界。

| 编号 | 优先级 | 问题与影响 | 代码依据 |
|---|---|---|---|
| R01 | 高 | ACTIVE Viewer 无条件计入占用，回收只处理 JOINING；失去心跳后可能永久占用 | `internal/store/rtc.go:817`、`:1012` |

### 5.3 测试自身的风险

- `internal/integration/p1_test.go:737` 的连接拒绝辅助函数先 Disconnect，再用 IsConnected 判断是否被允许，可能把错误放行判断为通过。未知设备、错误口令、APP 身份和故障拒绝等断言应修正后重跑。
- P2 的人工媒体事件和 TestProvider 只能证明部分数据库约束，不能证明真实媒体权限、共享资源删除和设备开关流正确。
- 部分旧事件测试选择了当前本身无副作用的 room_closed，需改用具有实际状态影响的事件补证轮次保护。
- 默认 `go test ./...` 不执行带 integration build tag 的测试，不能代表 HTTP 和 Store 数据库链路已经回归。
