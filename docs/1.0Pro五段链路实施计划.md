# 1.0Pro 五段链路实施计划

**日期：** 2026-11-20  
**调整：** 2026-11-20。MQTT 收归 eco-iot。cs 上只留 Device-Server 的那一只 EMQX。`eco-device-server` 只做语音 SFU。  
**依据：** `1.0Pro接入与MQTT-WS方案_纪要.md`（v2），以及 App、ECO、eco-iot、ECO-Device-Server 的现有代码。  
**目标链路：** App ↔ ECO 网关 ↔ eco-iot ↔ EMQX ↔ 硬件。通话媒体走 `eco-device-server` 的 SFU，不进 EMQX。  
**做法：** 一次只做下面的一步。上一步写出结果再进入下一步。某步的通过条件没达到就停，不把缺口改成放行。

几米保持暂停。可靠命令、可靠事件、视频编排、配网编排保持关闭。不把任何能力记成可切流。不在 116 和 cs 之间再搭 MQTT 桥。`iot-adapter` 继续停止。

## 1. 本计划采用的口径

这些口径按终态固定，执行时不再重开。

## 3. 分步

**通过：** 用测试客户端向本机 broker 发一条 `pet/collar/1_0pro/{mac}/state`，eco-iot 留下这条上报。再发一条旧的 `pet/collar/{mac}/state`，仍走原来的处理。两条互不覆盖。

**结果（2026-11-20）：** 已接上。`pet/collar/1_0pro/+/state` 和 `pet/collar/2_0_test/+/state` 用同一解析，原文按 `schema_id=petcollar.1_0pro` 写入原始日志。解析失败丢弃。旧的 `pet/collar/+/state` 仍走原来的解码。本机 mosquitto 上发一条定位上报后，记录留在 `1_0pro` 主题，没有改设备行，也没有发布 `cmd`。cs 上只换了 `eco-iot`，镜像 `eco-platform:f5e9737e`。`eco-platform:latest` 和 `eco-gateway` 没动。broker 上这三条订阅都在，五个迁入开关仍是关，`iot-adapter` 仍是停的。

### 步骤 2：同一台项圈在两边登记

在 ECO 的设备表登记这台项圈，序列号用 12 位小写 MAC，归属写 App 用户。在 Device-Server 把同一 MAC 登记为 `1_0pro`。App 认人只看 ECO 这一行。Device-Server 的 `dev` 租户和 `admin` / `operator` 不发给 App。

没有 ECO 设备行的上报只记日志，不推给页面，也不建一份新主人。

**通过：** 用同一个 MAC 能在 ECO 查到 App 用户，在 Device-Server 查到代次 `1_0pro`。未登记 MAC 的上报不出现在任何用户的页面数据里。

**结果（2026-11-20）：** `9030d6cb2703` 已登记。ECO 里序列号是这个 MAC，名称是「猫狗项圈 1.0 Pro」，厂商 `petcollar`，类型是项圈，归属是指定的 App 用户，绑定代次是 1。Device-Server 的 `dev` 租户里同一 MAC 的产品是 `collar`，代次是 `1_0pro`，没有把这个租户的账号授给 App。`447b304e3d24`、`689dd276f740`、`447b304e6a20`、`447b304e6530`、`447b304ee178`、`689dd277d3c8` 是 `2_0_test`，这一步没有登记。未登记上报只记日志的代码还在本地，cs 上的 `eco-iot` 仍是 `f5e9737e`。

这一步之后，连接和发令改看 ECO 设备行和 EMQX 允许表。不再往 Device-Server 的设备表补登记。

### 步骤 3：收成一只 EMQX，eco-iot 改接过去

留下 `eco-device-emqx`，停掉 `eco-emqx`。留下的这一只改用内置认证和授权，不再回调 `eco-device-server`。`eco-device-server` 断开自己的 MQTT 连接；SFU、`18196`、UDP `40100–40131`、`eco-device-mysql`、`eco-device-redis` 保持运行。

1. 先看 `eco-device-emqx` 上的客户端。除 `eco-device-server` 自己的服务连接外还有设备，就停，不改认证。

3. 在留下的 EMQX 上写内置认证。eco-iot 的允许表先与 `eco-emqx` 上已经生效的一致：当时的 14 个订阅，以及 `device/+/cmd`、`device/cmd/petcollar/+`、`device/+/archive/clear`。另给已经在 ECO 登记的 MAC 写下设备规则：用户名 `root`，客户端 ID 为该 MAC，只能发布自己这一代次的 `state`、订阅自己的 `cmd`。不建 `iot-dev-service`。此步仍不放行 eco-iot 发布 `pet/collar/.../cmd`。

**通过：** eco-iot 连在 `11883` 上，原来的订阅都在，并能收到一条 `pet/collar/1_0pro/{mac}/state` 测试上报。匿名、`root` 配未登记 MAC、以及未带账号的连接被拒绝。eco-iot 向 `pet/collar/.../cmd` 发布被拒绝。`eco-emqx` 已停。`eco-device-server` 没有 MQTT 连接，SFU 仍在 `127.0.0.1:18096`。

### 步骤 4：下行由 eco-iot 发布 `cmd`

App 的项圈指令进入 ECO 网关，网关交给 eco-iot。eco-iot 按 ECO 设备行核对用户后，自己发布 `pet/collar/{代次}/{mac}/cmd`。命令状态写在 `eco-mysql`。不调用 Device-Server 的 `POST /api/v1/devices/{id}/commands`。

这一步开始前，先把 eco-iot 发布具体设备 `pet/collar/1_0pro/{mac}/cmd` 和 `pet/collar/2_0_test/{mac}/cmd` 的规则加进允许表。仍然不放行带 `+` 或 `#` 的 `cmd` 过滤器。

App 不连接 `eco-device-server`。命令名先接寻宠和定位：`find_light`、`buzzer`、`gps_oneshot`。`voice_call` 等到步骤 7。其余命令等这三条走通再加。

**通过：** App 发出 `find_light` 后，设备收到对应 `cmd`。设备在 `state` 上的 `cmd_result` 在 eco-iot 的上报里对上同一次命令。用户不是该设备主人时，网关拒绝，eco-iot 不发布。

**结果（2026-11-21）：** 通过条件已达到。步骤 3 没有做完：`eco-emqx` 仍在跑，对外端口仍是 `11884`，`eco-device-server` 的 MQTT 连接没断，留下的 EMQX 也还没改成内置认证。这一步是在 `eco-device-emqx` 上做的。

允许表给账号 `eco-iot` 增加了具体设备的 `pet/collar/1_0pro/{mac}/cmd` 和 `pet/collar/2_0_test/{mac}/cmd`。带 `+` 或 `#` 的 `cmd` 仍拒绝。Device-Server 提交 `048a9e7`。cs 上挂载的 `config.docker.yaml` 把 eco-iot 的 broker 改成 `tcp://eco-device-emqx:1883`，这个地址没有提交。只重建了 eco-iot。`eco-platform:latest` 没改标签，`eco-gateway` 没重建。

ECO `02b3d91e` 起，设备行有 `topic_model`。`9030d6cb2703` 写成 `1_0pro`，命令发到 `pet/collar/1_0pro/{mac}/cmd`。六个 `2_0_test` MAC 没有登记，也没有改代次。开放的命令是 `find_light`、`buzzer`、`gps_oneshot`。App 提交 `6b8575ba`，其它命令名在进网关前拒绝。不调用 Device-Server 的发令接口。命令记在 `eco_iot.device_command_log`。

主人对 `9030d6cb2703` 发 `find_light`，网关返回成功，设备订着的 `cmd` 收到报文，并在 `state` 上回了 `{"ts":1795254506,"type":"cmd_result","cmd":"find_light","result":"accepted","code":0}`。这条对上同一次命令，记录 id 11 写成已确认。不是主人的请求被拒绝，eco-iot 没有发布，对应记录是失败。第一次部署时回执解析少了 `ts` 和 `type`，合法回执对不上待确认记录；`bc7e1475` 改成和校验用同一份字段。cs 上的 eco-iot 现为 `eco-platform:bc7e1475`，其中包含未登记上报只记日志的 `595c565f`。更早几条仍待确认的 `find_light` 没有回填，匹配只改同一命令最新的一条。

开机时带 `fw`、`hw` 的 JSON，以及带 `msgId` 的姿态，这一步仍然丢掉。这两类不在本步的通过条件里。

### 步骤 5：上行推进现成 WebSocket

eco-iot 把 `1_0pro` 的姿态、定位和命令回执推进网关已有的 `/api/v1/ws`。姿态沿用 `pet_pose:{deviceId}` 和类型 `pet_pose`。定位、命令回执各用一个新 topic 和对应 `type`，帧形与现有 `wsServerMsg` 相同：`type`、`topic`、`data`。

为这三种数据各提供一个补齐查询。查询返回的 `data` 与对应推送的 `data` 相同。断线后客户端只补一次，失败则按 `topicWs` 已有的退避重连，不另写一套心跳。

猫狗项圈页进入时只靠这些订阅刷新姿态、定位和命令结果。离开页面或关闭 App 时关闭连接。上报只由 eco-iot 接收。

**通过：** 设备上报一条姿态后，已打开的项圈页收到一条 `pet_pose`，页面不为这条数据发起轮询。断开后再请求补齐接口，得到与最后一条推送相同的 `data`。另一个用户的连接收不到这台设备的帧。

### 步骤 6：异宠中控去掉长轮询

中控的开关和温湿度进入同一种 WebSocket。topic 使用页面设备号，帧的 `data` 与补齐查询一致。`modules/reptile/utils/envSync.ts` 的 `/env/watch` 不再作为控制页的刷新方式。

下发仍由 eco-iot 写 `device/{mqtt_id}/property/set`，不经过 `eco-device-server`。116 上现有的 `ECO_IOT_CONTROLLER` 测试入口保持可用，直到这一页的正式网关路径接上后再删。删的时候只删这个测试入口，不改步骤 4 的项圈命令路径。

cs 的中控开关仍保持关闭。这一步不把 116 的板子改到 cs，也不把中控写进项圈 EMQX 的设备账号。

**通过：** 打开中控页只建立 WebSocket。设备自己改变开关后，页面收到推送。离开页面后连接关闭。断线补齐的 `data` 与推送一致。定时和开关命令仍发到板子当前所在的 broker。

### 步骤 7：音频双工到达 App

硬件已确认：没有第二路实时分析流，通话结束也不再开分析流。分析按录音上传，命令是 `mic_record`。录音怎么上传、怎么分析不在这一步，仍按协议另行约定。这一步只做 `voice_call`。

按现在的现场做，不回头做步骤 3、5、6：

- 步骤 3 未完成。`eco-emqx` 仍在，对外端口仍是 `11884`，`eco-device-server` 的 MQTT 还连着。通话命令由 eco-iot 发到 `eco-device-emqx` 上已有的 `pet/collar/{代次}/{mac}/cmd`。不改端口，不停 `eco-emqx`，不断那条 MQTT。
- 步骤 5 的页面联调未完成，不挡这一步。步骤 6 不动。cs 的中控开关保持关闭。
- SFU 已在 `127.0.0.1:18096`。设备使用 `http://120.25.100.77:18196`。RTP 使用 UDP `40100–40131`。

执行：

1. `eco-device-server` 在内部监听上增加签发接口，不挂到业务口，不发布 MQTT。开启时建房间，签发 `call:{mac}` 和 `call:u{用户号}`，有效 10 分钟。`whip_url` 必须是公网地址。出现 `127.0.0.1` 或 `localhost` 就拒绝签发。
2. eco-iot 在主人发起 `voice_call` 且 `on` 为 `true` 时调用该接口。设备凭证放进 `cmd` 的 `params`：`whip_url`、`token`，以及可选的 `duration_min`（1–60）。由 eco-iot 发布。App 凭证放在网关这次命令的响应里，字段是 `webrtc.whip_url`、`webrtc.token`、`webrtc.expires_at`。两张凭证不同。`on` 为 `false` 时只发布 `{"cmd":"voice_call","on":false}`，不再建房间。不是主人不发布。签发失败不发布。
3. App 服务放行 `voice_call`。`mic_record` 和其他命令名仍然拒绝。App 不连接 Device-Server，不拿到 `127.0.0.1:18096`，也不拿到设备那张凭证。通话只和 APP 对接。现有项圈页不加通话入口，这一步也不做通话界面。
4. 不把这路音频转给观看会话，不接涂鸦 WebRTC。不改 `eco-device-mysql` 和 `eco-device-redis` 的职责。

**通过：** App 发起 `voice_call` 后能听到设备。观看会话收不到这路通话。挂断后 eco-iot 发出 `on: false`。

### 步骤 8：中控主题与项圈对齐

这一步等待硬件确认中控的品类词。确认前不改 `device/+/property/*`，也不改 116 正在使用的板子。

确认后新增 `pet/{品类}/...` 订阅，固件切换期间旧主题继续接收。两套主题都指向同一台 ECO 设备。固件全部切完之后，再单独删旧订阅。

**通过：** 新主题的上报和 `property/set` 的现有页面操作指向同一台设备、同一个 App 用户。切换期间旧主题的命令和上报不丢。

### 步骤 9：写明兼容层的去留

单独决定 `device/telemetry/petcollar/v2/+` 和 `cat/event` 保留还是迁移。保留就在接入说明里写成兼容层，并写明对应的 `schema_id`。迁移就列出仍在使用的设备，逐台切完再删订阅。

绑定兜底「没有适配 topic 时按 SN 找厂商」在这一步用一条带 `1_0pro` 的上报验证。能匹配到步骤 2 的设备则保留兜底；匹配错厂商则收紧规则，不在前面的步骤里改它。

**通过：** 说明里有明确的保留或删除结论。在网设备的上报仍然进入原主人的页面。

## 4. 完成时的链路

| 方向 | 路径 |
| --- | --- |
| 项圈下行 | App → ECO 网关 → eco-iot → `pet/collar/1_0pro/{mac}/cmd` → 项圈 |
| 项圈上行 | 项圈 → `state` → eco-iot → 网关 WebSocket → App |
| 中控下行 | App → ECO 网关 → eco-iot → `device/{mqtt_id}/property/set` → 中控板 |
| 中控上行 | 中控板 → `property/report` → eco-iot → 网关 WebSocket → App |
| 音频 | App → ECO 网关 → eco-iot 取凭证并发布 `voice_call` → 项圈用 WHIP 进入 `eco-device-server` 的 SFU |

步骤 8 完成之前，中控上行和下行保持上表这一行。步骤 8 完成后，中控主题改为硬件确认的 `pet/{品类}/...`，页面和用户不变。

## 5. 完成时 cs 上与这条链路有关的服务

| 服务 | 功能 |
| --- | --- |
| EMQX（只留 Device-Server 这一只） | 接受项圈和 eco-iot 的连接，用内置账号做认证和 ACL，转发报文。设备使用 `tcp://120.25.100.77:11884`，同一进程也发布 `11883`。eco-iot 在容器网络里连接 `tcp://eco-emqx:1883` |
| eco-iot | 全部 MQTT 业务：订阅上报，发布项圈 `cmd` 和现有设备指令，核对命令回执，写入 `eco-mysql`，推给网关。UDP `40000–40063` 仍由这个进程占用 |
| eco-device-server | 只做 Pion SFU，监听 `127.0.0.1:18096`。建立通话房间，签发 `call:{mac}` 和 `call:u{用户号}` 凭证。不连接 EMQX |
| 宿主机 `18196` | 把设备的 WHIP 转到 `127.0.0.1:18096` |
| UDP `40100–40131` | 通话 RTP。不进 EMQX，也不转给观看会话 |
| eco-device-mysql | `eco-device-server` 的业务房间要等这台库就绪后才创建 |
| eco-device-redis | 只给 `eco-device-server` 做登录和发令限流 |
| eco-gateway | App 的 HTTP 入口和 `/api/v1/ws` |
| eco-mysql | 用户、设备、上报和命令状态 |
| eco-redis | ECO 现有的缓存和会话 |
| eco-pet、eco-horse、eco-exotic | 继续接收 eco-iot 转来的宠物、马和异宠业务数据 |

网关后面的 App、管理端、商户端、账号，以及 RabbitMQ、InfluxDB 保持原职责。`eco-emqx` 到完成时已经停掉。
