# 自研 EMQX 分步实施操作手册

## 1. 使用说明

**依据文档：** [自研EMQX完整实施方案.md](./自研EMQX完整实施方案.md)，V1.0。  
**建设范围：** 面向第一阶段 10,000 台设备，实现 EMQX + Go + MySQL + Redis + WebRTC 的设备接入、管理、观看、通话及生产运维能力。  
**文档性质：** 将总体方案拆成可安排开发、执行联调和逐项验收的操作任务，不表示相关功能已经实现。  
**执行方式：** 默认按任务编号从 S01 执行至 S43；任务只有在完成交付物、通过验收后才能勾选。

**AI 实施补充：** 配合 V3.0 分步实施计划时，S01-S43 是 AI 内部执行与技术检查清单，不代表每项都要人工签收。AI 在获准的 P 阶段包内按依赖连续设计、实现、自测、修复并自动维护一份进度记录；你只集中确认 G0-G5、PoC、上线就绪评审及真正需要人工决定/授权的例外。过程记录由 AI 整理，不要求你逐项填表；真实验证和权限边界不因此省略。

**环境顺序补充：** S40 可先完成生产等价部署/切换演练，S41 在该环境验证恢复；真实生产落地和 S40 的生产证据在上线授权后补齐，未完成时保持“生产待验证”。首次生产变更前必须已有适用的备份与恢复准备，不能以阶段编号为由跳过。

执行约定：

- 每个任务开始前检查“前置”，结束时保存代码版本、配置版本、测试记录或评审记录。
- 原方案未确定的产品版本、设备协议、网络端口、时间阈值、容量及部署平台，先按本手册完成决策，不把示例值当作生产参数。
- 本文给出的 API 扩展、数据约束和任务实现方式是落地建议，应在相应设计任务中确认后实施。
- Go 采用模块化单体；从首版起支持多实例；媒体流不经 Go 业务服务转发。
- 第一阶段只运行一个实际 Media Provider，不实施多厂商动态调度、自研 SFU、跨地域媒体调度、复杂录制转码和多设备会议。
- 媒体 PoC 可以在基础协议和 Provider 最小契约确定后提前进行，但不允许跳过真实设备验证直接上线。

## 2. 总执行顺序

| 顺序 | 任务范围 | 阶段目标 | 进入下一阶段的关卡 |
|---|---|---|---|
| 准备阶段 | S01-S04 | 明确范围、协议、环境、验收目标 | G0：关键依赖有负责人和结论或明确阻塞项 |
| 阶段一 | S05-S15 | 基础工程、用户权限、设备和 MQTT 闭环 | G1：真实设备可认证、上报、收令和回执 |
| 阶段二 | S16-S23 | 建立厂商无关 RTC 模型和可靠任务体系 | G2：使用测试替身通过状态机与多实例测试 |
| 阶段三 | S24-S27 | 真实设备 PoC、一个 Provider 和客户端适配 | G3：真实设备与 APP 可收发媒体并完成回调 |
| 阶段四 | S28-S34 | 单向观看、多 Viewer、关流、换票和通话 | G4：完整业务闭环和异常场景通过 |
| 阶段五 | S35-S43 | 恢复、安全、容量、部署、灰度和交付 | G5：生产上线验收通过 |

严格串行的主链路：

```text
S01-S04 -> S05-S15 -> S16-S23 -> S24-S27
        -> S28-S34 -> S35-S43
```

可提前或并行的工作只限以下边界：

- S03 环境准备和 S04 验收指标整理可在 S02 协议核查期间进行。
- S24 真实媒体 PoC 可在 S02、S03、S22 最小接口契约完成后提前启动；S25 的正式适配不得早于选型结论。
- APP 和设备团队可依据冻结的契约并行开发，最终必须在 S27、S28、S33 使用真实客户端联合验收。
- 日志、安全、测试随各任务实现，S35-S39 是集中核验，不是推迟到项目末尾才开始建设。

## 3. 准备阶段：消除实施阻塞

### S01. 建立实施范围和交付台账

**前置：** 已阅读原方案，确定项目负责人。

1. 建立任务台账，按本文编号录入负责人、协作方、开始条件、交付位置和验收人。
2. 将原方案第一阶段能力逐项登记：产品、设备、用户授权、MQTT、Ticket、Session、Viewer、Call、Provider、任务、运维。
3. 明确首期不做的能力，防止将录制、转码、多 Provider 调度等隐性加入开发范围。
4. 明确服务端、设备固件、APP、测试和运维的职责；协议问题由对应双方共同确认。
5. 约定变更流程：需求或协议发生变化时，更新决策记录、接口版本和受影响测试，不在联调时口头变更。

**交付物：** 范围清单、任务台账、人员职责表、变更记录模板。  
**验收：** 原方案最终交付清单全部有对应任务，无无人负责的关键交付。

### S02. 核查设备与 APP 能力，冻结首版通信契约

**前置：** S01。

1. 获取真实设备、可调试固件、设备 WebRTC SDK 资料、APP 工程及双方调试负责人。
2. 抓取现有 MQTT 连接与消息样本，记录客户端 ID、认证方式、Topic、QoS、保留消息、遗嘱、重连和回执行为。
3. 逐项确认设备 SDP、ICE Candidate、信令协议、DTLS/SRTP、音视频编码、麦克风、扬声器、摄像头及断线重连能力。
4. 确认开流、关流、流状态查询、通话邀请及接听拒绝方式；确认能否携带和回传 `request_id`、`session_id` 和版本信息。
5. 确认多通道、多清晰度是独立发布、同房多 Track 还是其他方式；绘制业务流与设备物理流的对应关系。
6. 定义统一消息外壳、设备身份映射、错误码和时间单位；兼容已有稳定协议，不为形式统一强改设备。
7. 明确 APP 接口调用、MQTT 通知与媒体信令分别走哪条链路，以及设备如何安全获取自己的短期媒体凭证。
8. 对尚无结论的项目登记负责人、验证方式和最晚完成阶段；不能在设备不具备双向音频时把通话功能标记为可交付。

**交付物：** 设备能力矩阵、MQTT 协议样例、流控制协议、信令流程、待决问题清单。  
**验收：** MQTT 开发所需字段已确认；RTC 未决项明确阻塞 S24 或 S27，不能以“标准 WebRTC”替代兼容验证。

### S03. 准备环境、版本和网络资源

**前置：** S01；网络需求参考 S02。

1. 划分本地开发、联调、压测、生产环境，设备身份、数据库和密钥相互隔离。
2. 选择并锁定 Go、EMQX、MySQL、Redis 版本及镜像摘要；核验 EMQX 对应版本的认证、授权、事件接入、集群功能与许可证条件。
3. 确认部署平台、域名、证书、时间同步、内外网地址、可用网络出口和防火墙管理方式。
4. 按所选版本列出端口和访问方：MQTT/TLS、HTTP、管理面、媒体信令、媒体 UDP 及 TURN；管理面和数据存储默认不暴露公网。
5. 准备测试设备和手机，覆盖目标移动网络、家庭宽带、受限 NAT 等环境。
6. 建立密钥分发和配置注入机制，不将设备密码、数据库密码或媒体 API Secret 写入仓库。

**交付物：** 环境清单、版本锁定表、网络访问矩阵、证书及密钥管理方案。  
**验收：** 各环境可访问必要基础资源，跨环境连接被隔离；未选媒体服务器时只预留网络需求，不虚构最终配置。

### S04. 定义容量模型和验收指标

**前置：** S01，参考 S02-S03。

1. 将 10,000 台定义为设备规模目标，另外确认同时在线比例、APP MQTT 连接数、上报周期、消息大小和重连峰值。
2. 分别给出 RTC 发布设备数、同时观看数、每流观看人数、双向通话数及清晰度/帧率/码率分布。
3. 估算消息吞吐：`消息数/秒 = 在线设备数 × 单设备平均上报频率 + 事件、命令和 APP 流量`。
4. 分别估算媒体入站和出站带宽；出站按各流实际订阅人数累加，再计入协议开销和 TURN 转发成本，避免只按设备数估算。
5. 确定 API 延迟、命令超时、首帧耗时、连接成功率、可用性及数据恢复目标 RPO（可接受数据丢失范围）/RTO（恢复时间）的验收阈值和测量方式。
6. 将 Viewer 心跳、断线容忍、开关流超时、关流延迟、Join Credential TTL 和重试次数登记为待实测参数；指定最终冻结时间。

**交付物：** 容量模型、SLO/验收指标表、参数实验表。  
**验收：** 指标有目标、统计口径、采样窗口和责任人；无目标的数据不能作为压测通过的证据。

**G0 检查：** S01-S04 完成。MQTT 开发所需协议和环境已具备；RTC 未决风险已登记，影响范围与准入条件明确。

## 4. 阶段一：基础工程与设备接入

### S05. 初始化 Go 模块化单体与工程质量检查

**前置：** G0。

1. 在确定的业务仓库中初始化 Go Module，采用原方案第十二章的 `cmd`、`internal`、`migrations`、`configs`、`deployments` 等分层。
2. 建立配置加载、依赖组装、优雅退出、HTTP 服务和独立存活/就绪探针。
3. 约束 Handler 只处理协议，Service 处理业务，Repository 处理存储；厂商 SDK 仅允许出现在 Adapter 内。
4. 配置格式化、静态检查、单元测试、竞态检测和构建流水线；提供本地启动入口。
5. 让实例标识、配置版本和构建版本可查询，启动失败时输出明确原因且不泄露密钥。

**交付物：** 可构建工程、配置模板、启动入口、CI 基线。  
**验收：** 空业务服务可启动并优雅退出；在已初始化的 Go 仓库根目录执行 `go test ./...`、`go vet ./...`、`go test -race ./...` 通过。

### S06. 部署 MySQL、Redis、EMQX 开发与联调实例

**前置：** S03、S05。

1. 按锁定版本编写可重复部署配置，配置持久化目录、健康检查、资源限制和环境隔离。
2. 为 Go、迁移工具、EMQX 集成和运维建立独立最小权限账号，不让应用使用数据库管理员账号。
3. 设置 MySQL 字符集、时区、连接池和事务约定；设置 Redis 内存、淘汰与持久化策略。
4. 关闭匿名 MQTT 接入，限制 Dashboard/管理 API 访问；开发明文入口不得直接复制到生产。
5. Go 接入 MySQL、Redis、EMQX 客户端，配置超时、重试上限和连接状态日志。

**交付物：** 部署配置、账号权限表、连接配置模板。  
**验收：** 服务可连通依赖；依赖不可用时不会无限阻塞或误报就绪；重建开发实例不会丢失应持久化的数据。

### S07. 建立数据迁移和基础数据模型

**前置：** S05-S06。

1. 建立有序迁移脚本、迁移版本表和独立迁移流程，避免多个 Go 实例启动时争抢修改表结构。
2. 创建产品、设备、设备认证、设备能力、用户/身份映射、用户设备授权表。
3. 按 S02 的命名域确定设备、产品、租户之间的关联；若采用多租户 Topic，所有查询、唯一键和鉴权必须采用一致租户边界。
4. 为设备 ID、产品标识、授权关系设置适当唯一约束，明确禁用、删除和凭证撤销语义。
5. 创建属性、事件、命令记录及必要查询索引；明确历史数据保留周期，避免把无限消息历史塞入设备主表。
6. 准备联调种子数据：至少两个用户、两个权限不同的设备、一个禁用设备及不同租户数据（若启用多租户）。

**交付物：** 基础 ER 图、数据字典、迁移脚本、测试数据。  
**验收：** 空库可迁移至最新版本；重复执行迁移不会重复建表；唯一性、隔离性和常用查询已测试。

### S08. 实现 HTTP 基础与用户设备权限

**前置：** S07。

1. 对接确定的用户身份系统，校验令牌有效期和主体身份；不直接信任请求体中的 `user_id`。
2. 统一响应、错误码、参数校验、分页、请求 ID、超时和限流。
3. 实现产品、设备、状态和能力管理；覆盖原方案的设备创建、查询、状态、能力 API，补齐内部必需管理入口并记录权限。
4. 实现用户与设备的授权关系，分离设备管理、观看、通话、Ticket 管理权限。
5. 对用户可提交的设备、Session、Viewer、Call 等 ID 统一按资源归属授权，内部接口使用独立身份和网络边界。

**交付物：** 用户鉴权中间件、设备业务模块、权限矩阵、API 初稿。  
**验收：** 未登录、无设备权限、跨用户/跨租户、已撤销授权均不能访问受限资源；正常用户只能执行被授予的操作。

### S09. 实现设备身份配置与 EMQX 认证

**前置：** S02、S06-S08。

1. 确认每台设备独立身份和凭证生成、出厂灌装/注册、存储、轮换及吊销流程。
2. 采用所选 EMQX 版本支持的认证后端；需要 Go 回调时实现仅供 EMQX 使用的内部认证入口。
3. 校验设备凭证、设备启用状态、客户端 ID 与设备映射，避免由设备任意声明他人身份。
4. 明确认证超时、数据库异常、禁用设备及未知设备的拒绝策略，不在依赖异常时默认放行。
5. 接入 APP MQTT 独立身份体系，不与设备共用账号或复用管理员账号。

**交付物：** 认证实现、EMQX 认证配置、凭证轮换操作。  
**验收：** 合法设备与 APP 可接入；错误凭证、未知/禁用设备、已撤销凭证均被拒绝；认证日志不含明文密码。

### S10. 实现 MQTT ACL 和 Topic 权限矩阵

**前置：** S09。

1. 按 S02 冻结的 Topic 设计列出设备、APP、后台服务分别能发布和订阅的主题。
2. 属性/事件/状态由对应设备发布，命令由授权后台发布，回执由目标设备发布；RTC Topic 若双向使用，明确消息类型与发布主体。
3. 将经过认证的设备身份绑定 Topic 路径，验证消息体 `device_id` 与 Topic、认证身份一致。
4. 显式拒绝设备越权访问其他设备、跨租户主题、`#`/`+` 通配订阅和管理系统主题。
5. 验证 APP 授权撤销后的权限刷新、认证/ACL 缓存失效及既有连接处置。

**交付物：** 发布/订阅矩阵、ACL 实现与配置、越权测试集。  
**验收：** 允许项全部成功、拒绝项全部失败；合法身份不能通过修改 Topic 或消息体操作其他设备。

### S11. 实现设备上下线与独立状态管理

**前置：** S09-S10。

1. 选择所选 EMQX 版本可用的连接/断开事件接入方式，校验事件来源并定义重复、乱序处理规则。
2. 持久化 MQTT 状态、最后在线时间及连接实例/连接轮次等必要关联信息。
3. 为重连建立新轮次，旧连接的断开事件不能覆盖新连接的在线状态。
4. 独立存储 MQTT、RTC 连接和 Track 可用状态，对外状态接口分别返回，避免一个 `online` 字段混淆。
5. 建立 Redis 在线缓存及 MySQL/EMQX 状态核查入口，保留设备最后上报与服务端推断状态的区别。

**交付物：** 上下线处理器、状态查询 API、连接关联规则。  
**验收：** 正常连接、异常掉电、快速重连、旧断开事件迟到均正确；MQTT 上线不会直接把 RTC 标为可观看。

### S12. 实现属性与事件消息入站

**前置：** S07、S10-S11。

1. 实现 MQTT 订阅、协议解析、大小限制、类型校验和身份一致性检查。
2. 对重要消息以约定的业务范围和 `message_id` 建立幂等键；业务副作用不能只靠短期 Redis 去重保护。
3. 设计多实例消费方式，例如共享订阅或所选版本支持的可靠事件转发；明确顺序保证和重复投递边界。
4. 入站处理只在形成可恢复的持久化结果后确认完成；验证客户端库的确认机制，不能假设回调返回即具备业务可靠性。
5. 分离属性更新、事件记录和异常消息处理；对处理失败设置有界重试、隔离和人工重放入口。

**交付物：** 消息处理器、幂等约束、消费与重放方案。  
**验收：** 同一消息重复投递不重复产生业务副作用；畸形消息不阻塞正常消息；两实例运行结果正确，进程异常后可恢复处理。

### S13. 实现命令下发、回执与超时

**前置：** S12。

1. 创建命令时生成业务命令 ID，记录目标设备、调用者、参数、发送时间、状态和超时时间。
2. 先持久化发送意图，再通过 MQTT 发送；实现可扫描的待发送记录或等价可靠机制，修复数据库提交后进程崩溃的发送缺口。
3. 区分“已提交”“已发送”“设备已确认”“执行成功/失败”“超时”，不把 QoS 确认当作设备执行成功。
4. 按命令 ID 关联回执；重复回执幂等，旧回执不得倒退终态。
5. 按设备协议决定哪些命令可重试；仅对可安全重试操作自动重发，设备不支持幂等时记录限制并设计查询确认/人工处置。
6. 提供内部命令调用及状态查询能力，供后续流控制和通话邀请复用。

**交付物：** 命令服务、发送补偿器、回执处理器、超时扫描任务。  
**验收：** 正常、离线、拒绝、超时、重复回执和发送前后崩溃均有确定结果；非幂等命令不会被盲目重复执行。

### S14. 建立基础日志、指标和链路关联

**前置：** S05-S13。

1. 结构化记录请求 ID、消息 ID、命令 ID、设备 ID、实例 ID、错误码和耗时。
2. 在 HTTP、MQTT 消费、数据库调用和异步任务之间建立可追踪关联；后续加入 Session/Viewer/Call ID。
3. 接入 Prometheus/Grafana 及确定的日志平台，监控连接数、认证失败、消息速率、积压、处理延迟、命令超时和依赖错误。
4. 不将 Ticket、媒体凭证、密码写日志；高基数业务 ID 放日志/追踪，不直接作为 Prometheus 标签。
5. 设置初始告警并验证通知通道；将阈值在 S38-S39 后按实测调整。

**交付物：** 日志规范、基础仪表盘、追踪样例、告警规则。  
**验收：** 能从一次 API 调用定位到设备命令回执；模拟认证和依赖异常时能收到可定位的告警。

### S15. 验收设备接入闭环

**前置：** S05-S14。

1. 用真实设备执行注册/配置身份、MQTT 认证、属性上报、事件上报、命令下发、回执、断线和重连。
2. 用真实 APP 验证 MQTT 身份及允许的通知 Topic。
3. 同时运行至少两个 Go 实例，验证消息幂等、上下线乱序、实例停止和消费恢复。
4. 执行错误凭证、越权 Topic、畸形消息、数据库/Redis 短暂故障用例，记录结果。

**交付物：** 基础链路演示、集成测试报告、问题清单。  
**验收：** 设备消息和命令闭环可重复运行；阻断性问题归零。

**G1 检查：** 真实设备与 APP 的 MQTT 接入可用，设备管理、权限、数据存储和多实例处理已验证。

## 5. 阶段二：厂商无关 RTC 业务基础

### S16. 冻结 RTC 状态机、资源占用与数据库约束

**前置：** G1；业务维度参考 S02。

1. 为 Ticket、Session、Viewer、Call、Media Resource、任务建立数据字典和迁移脚本。
2. 为 Session、Viewer、Call 绘制完整状态迁移表，定义触发事件、允许源状态、目标状态、超时、失败和重复事件处理。
3. 按 `device_id/channel_id/stream_type/resolution` 确认 Session 复用键；统一空清晰度的表示，避免 NULL 破坏预期唯一性。
4. 设计“同业务流仅一个当前有效 Session”和“同设备仅一个主通话”的数据库保障。可用独立占用行的唯一键加事务，历史表只保留完整历史。
5. 区分资源轮次 `generation` 与并发更新版本；明确哪些操作递增轮次、哪些任务必须失效，禁止仅加字段而无更新规则。
6. 定义流使用者集合：有效 Viewer、建连宽限期内的 JOINING Viewer、有效 Call 及正在进行的合法占用，不能只统计 ACTIVE Viewer。
7. 若多个 Session 共用一条物理流或一个 Room，建立共享资源归属和使用检查，防止关闭某个 Session 时影响其他通道、清晰度或通话。

**交付物：** 状态迁移表、ER 图、唯一性与事务设计、资源归属规则。  
**验收：** 每个终态、超时和异常路径都有定义；两个实例同时建流或通话不会突破唯一占用约束。

### S17. 实现持久化任务和跨实例协调

**前置：** S16。

1. 以 MySQL 任务表保存任务 ID、类型、业务 ID、轮次、状态、执行时间、重试次数和错误信息。
2. 补齐任务唯一键、执行租约/领取时间、执行实例及到期扫描索引；原子领取任务，防止两个 Worker 无控制地执行同一任务。
3. 支持运行中 Worker 崩溃后的租约回收、退避重试、最大次数和人工重试；任务副作用按至少一次执行设计幂等。
4. 将业务状态变更与任务创建放在同一事务，或采用已明确的等价可靠机制。
5. Redis 可保存到期索引、缓存和短期锁，但 MySQL 为任务恢复依据；Redis 清空后能重建索引。
6. 分布式锁采用唯一持有者令牌、安全释放和必要续租；关键正确性仍由数据库约束、条件更新和设备协议保障。
7. 任务执行前重新校验状态、轮次和资源使用者；外部调用期间锁过期或状态变化时，也不能直接写回成功。

**交付物：** 通用 Worker、任务仓储、Redis 键/TTL 规范、恢复测试。  
**验收：** 两实例抢占、Worker 强制终止、Redis 数据清空、任务重复执行均不丢失关键业务操作；无需依赖本地定时器维持正确性。

### S18. 实现 Ticket 创建、校验、换票和失效

**前置：** S08、S16-S17。

1. 实现创建、查询、换票接口；使用密码学安全随机值，不暴露自增 ID。确认 Ticket 查询权限、返回方式及存储保护。
2. 校验存在、状态、有效期、当前版本、设备、用户设备权限及本次操作权限。
3. 在事务中切换当前有效版本，使并发换票只能形成一个最终当前版本；旧版本不能再授权新观看、续签凭证或通话。
4. Ticket 缓存按版本失效；关键授权与换票竞争必须有明确线性化点，防止旧请求绕过已完成的换票。
5. 支持同 Ticket 被多个获授权用户、多个 IP 和客户端使用，不按用户/IP/清晰度/通道强行一票一绑。
6. 记录创建、换票、撤销和使用审计，不在普通访问日志中输出完整 Ticket。

**交付物：** Ticket 模块、API、换票事务、单元及并发测试。  
**验收：** 新票可用、旧票失效、过期被拒、无权限用户持票仍被拒；通道/清晰度切换不要求额外换票。

### S19. 实现 Session 状态机与并发创建

**前置：** S16-S18。

1. 实现创建/复用 Session、状态查询、条件更新和迁移审计，禁止业务模块绕过统一入口直接改状态。
2. 实现 `CREATED -> WAITING_DEVICE -> STREAM_STARTING -> ACTIVE -> STOP_PENDING -> STOPPING -> CLOSED` 的正常路径及明确的失败/超时路径。
3. 支持 `STOP_PENDING` 在新使用者加入时恢复；对 `STOPPING` 明确拒绝、等待或新轮次策略，不把它当作可立即复用的 ACTIVE Session。
4. Session 只有在设备和媒体就绪条件满足后进入 ACTIVE，不能因凭证返回或 MQTT 在线就标记成功。
5. 通过事务和唯一占用处理并发创建；验证旧 generation 的回执、任务和媒体事件无法覆盖新轮次。

**交付物：** Session Service、状态机、会话查询、并发测试。  
**验收：** 多请求同时观看同一业务流只形成一个当前有效 Session；非法迁移失败且原因可追踪。

### S20. 实现 Viewer 生命周期与心跳

**前置：** S19。

1. 每次独立观看生成 `viewer_id`，记录用户、客户端、Session、状态、时间和媒体身份映射。
2. 为创建请求设计幂等键，重试请求返回同一观看结果；同用户不同客户端可以各有独立 Viewer。
3. 实现 JOINING、ACTIVE、LEAVING、LEFT、DISCONNECTED 状态及允许的重连路径，设置 JOINING 建连宽限期。
4. 心跳只更新被授权且尚有效的 Viewer，不允许迟到心跳复活 LEFT 或已失效轮次。
5. 退出采用条件更新，仅首次成功退出改变资源使用关系；`viewer_count` 只做派生数据。
6. 超时扫描结合 Participant 状态二次确认，按网络测试结果调整阈值。

**交付物：** Viewer Service、心跳/退出接口、超时扫描、幂等测试。  
**验收：** 同用户多端互不踢出；重复退出不重复扣减；有合法 JOINING Viewer 时不会提前关流；旧心跳不能恢复终态。

### S21. 实现 DeviceStreamController 及安全关流骨架

**前置：** S02、S13、S17、S19-S20。

1. 定义 `StartStream`、`StopStream`、`GetStreamStatus`，请求至少关联设备、流维度、Session、request ID 和有效轮次。
2. 先实现可模拟成功、超时、重复、延迟、乱序和失败的测试 Controller，再实现 S02 已确认的实际设备控制方式；需要媒体侧能力的部分在 S27 联调闭合，不提前实现不存在的控制协议。
3. 开流、关流均记录意图和请求，重试复用业务幂等标识；回执必须关联请求，不能只按设备 ID 更新最新会话。
4. 实现无使用者时进入 STOP_PENDING 并持久化延迟任务；执行前再次检查 Viewer、Call、共享流使用者及 generation。
5. 明确“检查通过到关流命令生效”之间的竞态处理。若设备支持版本栅栏，让设备拒绝旧轮次命令；若不支持，必须采用串行化控制、停止完成前禁止复用及状态确认等可验证方案。
6. 对已发出但设备结果未知的 Stop 请求，不因本地锁释放就启动可能被旧命令关闭的新流；定义查询确认、等待或故障处置路径。

**交付物：** 流控制接口、测试及实际协议 Controller、延迟关流骨架、设备侧限制记录。  
**验收：** 旧任务、乱序命令和迟到回执不会误关或覆盖新会话；仅在应用层发送前检查 generation 不算完整验收。

### S22. 定义 Media Provider、资源映射与统一事件

**前置：** S16、S19；可先冻结最小契约以提前启动 S24。

1. 定义原方案的建房、删房、签发凭证、移除参与者、查询房间/参与者/轨道接口及统一模型。
2. 明确 Join 权限、凭证 TTL、Identity 生成、超时、幂等和错误分类；通用接口不包含厂商 SDK 类型。
3. 定义能力声明，业务按设备能力与 Provider 能力的交集放行；高级能力放独立扩展，不无限增加通用参数。
4. 实现媒体资源映射仓储，关联 Session、Provider、资源类型、厂商资源 ID、父资源和必要轮次信息。
5. 定义 Participant/Track 与 Viewer、Call、设备的关联，保证回调可以定位真实业务对象和所属轮次。
6. 设计外部建房成功但映射写库失败的补偿：使用业务关联标记、幂等创建或资源查询回收，避免无限泄漏。
7. 定义媒体事件 ID、类型、来源、发生时间、资源映射及处理状态；明确旧事件识别不能只依赖不可靠的跨机时间戳。
8. 实现测试 Provider，模拟资源和事件，不把模拟凭证当作可连接的 WebRTC 凭证。

**交付物：** Provider 契约、测试 Provider、映射仓储、统一事件模型。  
**验收：** 业务模块可只用测试 Provider 运行；无厂商 SDK 导入；业务 ID 与媒体资源 ID 独立。

### S23. 实现 Call 基础模型并验收 RTC 业务层

**前置：** S16-S22。

1. 实现 CREATED、RINGING、ACCEPTED、CONNECTED 及 REJECTED、TIMEOUT、ENDED、FAILED 状态机，定义取消、离线和接听后建连超时路径。
2. 在同一事务内获取设备主通话占用、创建 Call 和待发送邀请；占用从呼叫开始覆盖到终态释放。
3. 仅允许预期设备/接听主体变更通话状态，普通无关用户不能调用 accept/reject。
4. 通话占用释放必须匹配原 call ID，旧通话清理任务不能释放新通话占用。
5. 使用测试 Provider/Controller 跑通 Ticket、Session、Viewer、Call、持久化任务和媒体事件流程。
6. 执行状态机、重复请求、双实例并发、旧轮次事件和重启恢复测试，并运行竞态检测。

**交付物：** Call Service、设备占用实现、RTC 业务层测试报告。  
**验收：** 两实例同时呼叫同一设备只成功一个，其余返回设备忙；不依赖真实媒体服务器即可验证控制平面正确性。

**G2 检查：** RTC 模型、可靠任务、幂等和多实例约束通过；测试替身仅证明业务逻辑，不能替代 G3 的真实媒体验收。

## 6. 阶段三：真实媒体 PoC 与 Provider 接入

### S24. 使用真实设备和 APP 完成媒体服务器 PoC

**前置：** S02、S03、S22 最小契约；正式接入前须通过 G2。

1. 依据设备 SDK、编码和信令能力筛选候选方案，比较 LiveKit、Janus、mediasoup 或其他满足要求的产品，不预先认定某一产品。
2. 部署一个优先候选的隔离 PoC 环境，记录版本、授权许可、部署依赖、TLS 和网络路径；失败再依据证据评估其他候选。
3. 用真实设备发布视频，真实 APP 订阅，再增加多个 APP 同时观看。
4. 验证双方音视频发布/订阅、设备实际采集播放、麦克风权限和最小 Participant 管理能力。
5. 验证家庭宽带、移动网络、网络切换及强制 TURN 路径，记录 ICE 类型、连接成功率、首帧、丢包、时延和带宽。
6. 验证事件回调、查询接口、踢人/撤权能力、进程重启及资源清理方式。
7. 记录 SDK 适配工作量、部署与扩容方式、许可证及商用条件、成本和不满足项。
8. 形成一个首期 Provider 的选型结论；核心场景失败则保持阻塞并调整设备适配或候选，不以浏览器演示替代设备结果。

**交付物：** PoC 脚本/配置、真实设备测试记录、兼容矩阵、选型决策。  
**验收：** 单向、多观看、双向、穿透和回调均有证据；容量结论只限 PoC 实测范围，最终容量由 S39 确认。

### S25. 实现唯一一个正式 Provider Adapter

**前置：** G2、S24。

1. 在 Adapter 目录接入选定 SDK，完成统一请求/返回值转换、超时、错误映射和权限生成。
2. 实现 Provider 工厂、配置校验、能力声明及依赖健康检查；错误 Provider 名称、缺失密钥或错误配置明确失败，不静默切换。
3. 实现房间和参与者的创建、查询、删除/移除、轨道查询及短期加入凭证签发。
4. 观看者默认只订阅；设备按能力发布；通话 APP 仅获本次通话必要的发布/订阅权限。
5. 将媒体凭证绑定到业务 Identity 和目标资源；密钥仅服务端持有，Join Credential 不等于 Device Ticket。
6. 验证重复创建、重复删除、请求超时和部分成功后的查询补偿，防止创建孤儿资源。

**交付物：** 一个真实 Adapter、契约测试、环境配置模板。  
**验收：** 相同业务测试可替换测试 Provider 为真实 Adapter；核心业务无厂商数据结构泄漏。

### S26. 实现媒体事件安全接入与可靠处理

**前置：** S17、S22、S25。

1. 实现 `/api/v1/internal/media/events` 或与所选 Provider 匹配的内部接入端点。
2. 按 Provider 官方机制校验来源、原始请求签名、时间窗口和事件 ID；适配层完成校验后再转换统一事件。
3. 将合法事件先可靠落库，再异步处理；以 Provider 和事件 ID 建立幂等约束，重试窗口覆盖实际投递周期。
4. 映射 participant joined/left、track published/unpublished、room closed、connection failed 到业务事件。
5. 按资源轮次、允许迁移和必要的 Provider 查询处理重复、乱序与迟到事件，不允许旧 left 事件覆盖新连接。
6. 对暂时找不到业务映射的事件做有界重试或隔离，提供回放和审计；伪造事件不进入业务处理链路。

**交付物：** 事件入口、签名验证、事件持久化与重放、状态同步处理器。  
**验收：** 重复事件只产生一次逻辑效果，乱序不倒退状态；进程停止后已接收事件可恢复；伪造/过期请求被拒绝。

### S27. 完成设备与 APP 信令/媒体适配

**前置：** S02、S24-S26。

1. 设备端实现选定媒体服务器所需信令适配、短期身份获取、轨道发布、远端轨道订阅和重连。
2. APP 实现连接信息解析、加入、订阅、通话发布、音频路由和网络切换恢复；凭证不得跨 Viewer/Call 任意复用。
3. 部署或接入已确认的 STUN/TURN，配置证书、认证和中继范围；测试公网不可达时的失败反馈。
4. 将设备开流、实际 PeerConnection、Participant 和 Track 事件串联到 Session/Viewer 状态。
5. 记录客户端 SDK、固件、APP 与 Provider 的兼容版本，隔离厂商信令适配与业务界面逻辑。

**交付物：** 可联调固件、APP 构建、信令适配、媒体部署及连接排障说明。  
**验收：** 真实设备和 APP 在目标网络中建立连接，Track 可见且可播放；双向能力在硬件上实际可用；TURN 路径有验证记录。

**G3 检查：** 仅一个 Provider 正式接入；真实客户端与设备媒体链路、统一事件、安全和资源查询可用。

## 7. 阶段四：完整观看与通话业务

### S28. 串联单向观看完整链路

**前置：** G3、S18-S21。

1. APP 提交 Ticket 和设备流参数，服务端从身份上下文取得用户并检查观看权限和设备能力。
2. 在数据库事务中原子创建/复用有效 Session 及必要的业务意图，再按可恢复步骤调用外部媒体 API、保存资源映射和创建 Viewer；跨系统不假设一个本地事务可整体回滚，逐步记录失败补偿责任。
3. 根据设备协议执行实际 Controller，安全向设备交付其专属凭证/连接信息；向 APP 返回 Viewer ID、Session ID、短期凭证和状态。
4. 处理 API 超时重试、签发失败、设备离线、媒体建房失败；不能留下永久 JOINING Viewer 或无主媒体资源。
5. APP 等待真实媒体就绪，服务端结合 Participant/Track 确认 ACTIVE；签发成功但开流失败要能查询到失败原因。
6. 记录请求至首帧的端到端耗时，区分鉴权、设备唤起、ICE 和媒体订阅耗时。

**交付物：** 可演示观看链路、接口样例、失败补偿测试。  
**验收：** 有权限用户可观看正确设备/通道/清晰度；无权限和旧 Ticket 被拒；MQTT 在线但无 Track 时不报告视频可用。

### S29. 验证多用户、多客户端观看与重连

**前置：** S28。

1. 使用同一 Ticket，分别测试不同获授权用户、不同 IP、同用户不同客户端同时观看。
2. 并发请求相同业务流，检查只有一个当前有效 Session，每次独立观看有独立 Viewer 和媒体 Identity。
3. 在不同通道/清晰度间切换，按 S16 规则复用或创建 Session；不要求为同设备每个通道重新申请 Ticket。
4. 测试单 Viewer 退出、APP 强杀、网络切换和心跳中断，确认其他 Viewer 不受影响。
5. 验证短期凭证续签或重连重新授权，业务权限撤销、旧 Ticket 和已终止 Viewer 不能继续获取新凭证。

**交付物：** 多端矩阵、重连与续签流程、并发集成报告。  
**验收：** 同用户多端互不覆盖；凭证和 Participant 归属可追踪；无重复开流和错误关流。

### S30. 完成延迟关流、取消与竞态联调

**前置：** S17、S21、S29。

1. 最后一个合法使用者退出后，事务更新 STOP_PENDING 并写入带轮次的持久化任务。
2. 到期 Worker 重新读取 Viewer 明细、有效 Call、Session/物理流使用关系和 generation，满足条件才进入 STOPPING。
3. 在 STOP_PENDING 期间加入新 Viewer，取消或使旧任务失效，并验证旧 Worker 已领取任务时同样安全。
4. 在 STOPPING、命令已发送和回执延迟时加入新 Viewer，执行 S21 确认的等待/隔离/版本栅栏策略。
5. 确认设备和媒体实际停止后再 CLOSED，清理本 Session 所拥有且不再共享的资源；结果未知时保留可恢复状态和告警。
6. 在等待期和执行期分别终止 Go 实例，重启后继续任务；重复执行不产生额外副作用。

**交付物：** 可恢复延迟关流链路、竞态测试、未知结果处置说明。  
**验收：** 单人退出不影响他人，通话占用不被关闭，旧任务不会关闭新流；任务在重启和 Redis 索引丢失后可恢复。

### S31. 确认并实现换票及授权撤销的存量连接策略

**前置：** S18、S25、S28-S30。

1. 与业务方确认换票后已连接 Viewer/Call 的处理：允许本轮继续，还是主动断开。另行明确设备授权撤销、禁用及安全事件的处理策略。
2. 若允许本轮继续，禁止旧 Ticket 创建新 Viewer、续签或新通话，明确现有媒体连接的结束边界。
3. 若要求主动断开，基于资源映射移除相关 Participant、终止对应业务使用，并阻止旧凭证在剩余有效期内重入。
4. 核验 Provider 是否支持令牌撤销、加入校验、身份拒绝或等价隔离。单纯踢人不等于凭证失效；若无法满足立即撤销，必须调整策略并记录限制，不能宣称已实现。
5. 测试换票与正在进行的签发/加入竞争、缓存失效、接口重试及多用户共享 Ticket 场景。

**交付物：** 经确认的存量连接策略、实现与限制、换票安全测试。  
**验收：** 旧票不能形成新授权；存量连接行为与确认策略一致；不把 Ticket 失效误认为媒体连接自动断开。

### S32. 实现呼叫邀请、接听、拒绝、超时与占用

**前置：** S13、S23、S27-S31。

1. 发起呼叫前校验用户通话权限、设备在线/硬件能力和 Provider 能力，事务获取主通话占用。
2. 持久化 Call 和邀请发送任务，经确认的设备协议发送邀请，进入 RINGING。
3. 按真实身份校验设备接听/拒绝消息，关联 call ID 和 request ID，重复或迟到响应不能改变已结束通话。
4. 实现振铃超时、主叫取消、设备离线和接听后建连超时，保证所有终态释放自己的占用。
5. 第二个呼叫返回明确设备忙；普通 Viewer 是否继续观看按权限执行，不允许其自动获得麦克风发布权。

**交付物：** Call API、邀请/回执、超时任务、冲突处理。  
**验收：** 接听、拒绝、忙、取消、超时、迟到回执均可复现；多实例只允许一个主通话。

### S33. 完成双向媒体连接与结束清理

**前置：** S32。

1. 接听成功后创建或复用符合设备能力的媒体资源，分别签发 APP 和设备权限受限的短期凭证。
2. 按 Provider 实际能力约束可发布/订阅对象；普通观看者不能窃听 APP 上行私有音频，不能只靠 APP 界面隐藏或客户端自觉不订阅。
3. 若同房权限无法隔离通话与观看，调整资源分离或访问控制并重新联调，不强行复用同一个 Room。
4. 双方加入且必要音视频轨道、订阅就绪后进入 CONNECTED；仅收到设备接听不能标记通话已连接。
5. 实现挂断、设备离线、媒体失败、APP 强退和重连策略；终态仅清理本 Call 拥有的发布权限、Participant 和独占资源。
6. 有其他 Viewer 时保持其观看；无 Viewer 且无其他占用时进入统一延迟关流流程。

**交付物：** 双向通话链路、轨道权限配置、结束清理与重连测试。  
**验收：** 真实设备和 APP 能按能力双向收发；普通 Viewer 不能获取通话私有上行；通话结束不误关其他观看。

### S34. 固化 API 协议并执行完整端到端验收

**前置：** S28-S33。

1. 固化原方案第十一章接口的请求、响应、错误码、身份、权限、幂等键和异步状态查询方式。
2. 覆盖设备、Ticket、Session 创建/查询、Viewer 加入/退出/心跳、Call 创建/接听/拒绝/挂断/查询、内部媒体事件。
3. 补齐凭证续签、命令查询和必要管理操作的契约；产品与设备能力管理可采用内部接口，但必须有明确使用入口和权限。
4. 运行单向观看、多观看、换票、最后使用者关流、双向通话、冲突、断网重连及多通道/清晰度切换。
5. 固化可重复的测试数据、请求集合和自动化用例；固件、APP、服务端与配置使用同一兼容版本组合。

**交付物：** OpenAPI/接口文档、联调请求集、兼容版本表、端到端测试报告。  
**验收：** 所有对外接口均有权限说明与正反向用例，核心链路无阻断问题。

**G4 检查：** 单向观看、多 Viewer、换票、延迟关流、双向通话及资源隔离形成真实业务闭环。

## 8. 阶段五：恢复、安全、容量与生产上线

### S35. 实现定时对账与人工恢复

**前置：** G4、S17、S26。

1. 扫描长时间 WAITING_DEVICE/STREAM_STARTING 的 Session，并结合命令、设备和媒体查询决定重试、失败或清理。
2. 扫描心跳超时 Viewer，对照 Participant 状态修复业务记录与媒体实际状态差异。
3. 扫描无合法使用者仍运行的流、已关闭但仍有资源的 Session、过期 JOINING Viewer 和孤儿 Room/Participant。
4. 扫描未知结果的开关流、超时命令、长期异常 Call、未释放占用及租约过期任务。
5. 对账变更沿用正常状态机、版本校验和资源所有权规则；不要另写可绕过安全校验的“强制更新”逻辑。
6. 提供查询、重试、取消、资源隔离/清理等受控人工入口，审计操作人和原因。

**交付物：** 对账 Worker、异常仪表盘、人工恢复操作说明。  
**验收：** 人工制造事件丢失和孤儿资源可被发现并有界修复；重复对账不误伤健康会话，失败可告警和升级人工处理。

### S36. 完善 RTC 监控、告警和故障定位

**前置：** S14、S28-S35。

1. 采集 Session/Viewer/Call 数量及状态分布、Participant/Track 数量、发布成功率、媒体连接成功率和建立耗时。
2. 采集 ICE 成功率、首帧、重连、丢包、时延、TURN 比例及媒体服务器 CPU、内存、网络带宽。
3. 采集任务积压/最老等待时间、重试耗尽、对账差异、命令未知结果、数据库慢查询和 Redis 错误。
4. 以 S04 的口径设置告警，给出影响范围、定位入口和处置指引，避免只监控进程存活。
5. 将 APP/设备媒体质量遥测与服务端控制链路关联；凭证和敏感数据持续脱敏。

**交付物：** MQTT/RTC/基础设施仪表盘、告警规则、定位示例。  
**验收：** 能区分“MQTT 离线”“媒体建连失败”“有连接无 Track”“APP 未播放”“任务积压”等不同故障，并验证通知送达。

### S37. 执行安全测试和凭证轮换演练

**前置：** S31、S34-S36。

1. 核查生产 MQTT TLS、设备独立身份、Topic ACL、APP 身份、匿名入口关闭和管理面隔离。
2. 测试跨用户/租户资源访问、持票无权限、越权签发、观看者非法发布、通话轨道越权订阅及内部接口伪造。
3. 测试过期 Join Credential、旧 Ticket、签名伪造/重放、时间窗口、限流、异常大消息和频繁重连。
4. 按 API 风险使用合适的防重放和幂等机制；不能把“具备幂等键”直接等同于完成身份认证或防重放。
5. 扫描仓库、镜像、日志与依赖漏洞，验证敏感字段脱敏和最小权限账号。
6. 演练设备凭证、媒体 API 密钥、数据库凭证及证书轮换，记录存量连接处理和失败回退。

**交付物：** 安全测试报告、漏洞整改、轮换记录。  
**验收：** 无未处置的上线阻断安全问题；不能满足立即撤销的限制已落实到业务策略，而非仅写在备注中。

### S38. 执行全量自动化、并发和故障注入测试

**前置：** S34-S37。

1. 完整执行 Ticket、Session、Viewer、Call、Provider 参数转换、Controller 幂等和任务恢复的单元/集成测试。
2. 在至少两实例下并发执行多 Viewer 加入、最后 Viewer 退出同时加入、重复退出、并发主通话、迟到开流回执和旧关流任务。
3. 在数据库提交前后、外部 API 成功后写库前、任务领取后、MQTT 发送后回执前分别终止进程，检查补偿和重试。
4. 注入 MySQL/Redis/EMQX/媒体服务器短暂不可达、媒体事件重复/乱序/丢失、APP/设备断网和 TURN 异常。
5. 验证 Redis 锁到期、缓存清空和任务索引重建；验证 Go `go test -race ./...` 无数据竞争。
6. 按 S04 指标与真实网络结果冻结心跳、建连宽限、超时、延迟关流、重试和凭证 TTL，记录配置依据。

**交付物：** 自动化报告、故障注入报告、参数定版表。  
**验收：** 无重复主通话、误关新流、不可恢复任务、越权或状态永久悬挂；故障恢复时间符合目标，超出能力的场景有明确降级和人工路径。

### S39. 执行 MQTT、RTC 和数据层容量测试

**前置：** S04、S36-S38；使用隔离压测环境及固定版本。

1. 编写压测计划，固定客户端数量、上报周期、消息大小、QoS、视频参数、网络模型、持续时间和通过条件。
2. 分级增加至 10,000 台设备 MQTT 长连接，叠加目标 APP 连接及持续属性/事件流量，不以瞬时连上即视为通过。
3. 测试高频消息、批量上下线、掉线重连和命令回执；观测 EMQX、Go、MySQL、Redis 的吞吐、延迟、积压及错误。
4. 独立增加 RTC 发布、订阅、每流观看和双向通话并发，分别验证直连与 TURN 比例变化。
5. 测试多实例 Session/Viewer 写入竞争、任务领取、数据库索引与连接池；瓶颈优化后使用同一场景复测。
6. 记录正常负载、目标峰值、过载行为和资源余量，形成扩容阈值及限流/降级方案。
7. 区分模拟媒体、真实设备抽样与完整真实网络结果；只有与目标编码/码率/网络一致的测试才能支持对应容量结论。

**交付物：** 压测脚本、数据与曲线、瓶颈整改、容量与成本报告。  
**验收：** MQTT 目标规模与约定消息负载达标；RTC 按实际发布/订阅/通话目标达标，不把 10,000 台 MQTT 连接等同于 10,000 路视频。

### S40. 完成生产部署与多实例故障切换

**前置：** S03、S37-S39。

1. 按容量报告落实 EMQX 集群、Go 多实例、MySQL、Redis、媒体服务器和监控日志的独立部署与资源配额。
2. 明确各组件的高可用拓扑、故障域及单点；如接受某个单点，记录业务影响、恢复时限和批准结论。
3. 配置负载均衡、TLS、探针、优雅退出、连接排空和滚动发布；Go 实例退出不持有唯一业务状态。
4. MQTT 消费、持久化 Worker 和媒体回调均按多实例部署，校验连接重建、任务租约和事件投递。
5. 生产数据库迁移单独执行并检查兼容性；应用回滚不等于立即回滚数据库或删除新增列。
6. 演练一个 Go 实例退出、EMQX 节点故障、已配置的数据库/Redis 切换和媒体节点故障，记录媒体连接受损与重连边界。

**交付物：** 生产拓扑、部署清单、网络规则、滚动发布及故障切换记录。  
**验收：** 目标规模下节点故障影响可测、可恢复；不依赖单机 Viewer 列表、Mutex 或本地定时器维持全局正确性。

### S41. 完成备份、恢复与运维手册

**前置：** S35-S40。

1. 配置 MySQL 备份、保留、加密、异地/独立故障域存储和必要的时间点恢复能力，目标由 S04 的 RPO/RTO 决定。
2. 备份 EMQX、Redis、媒体服务器的必要配置及部署版本；密钥备份单独受控，不将业务缓存当主数据。
3. 在隔离环境执行恢复，核对设备身份、授权、Ticket 当前版本、会话历史、任务和审计完整性。
4. 数据库恢复后先隔离外部控制副作用，核对媒体实际状态和旧待执行任务，再有选择地恢复 Worker，防止恢复旧备份后重放过时关流。
5. 编写认证失败、命令超时、无首帧、TURN 失败、任务积压、孤儿资源、媒体故障及数据恢复的排障步骤。
6. 固化值班、升级联系人、人工干预权限、回滚顺序和灾难恢复演练周期。

**交付物：** 备份策略、恢复实测记录、部署/运维/故障手册。  
**验收：** 恢复不是“备份任务成功”截图；实际恢复耗时、数据丢失范围和恢复后状态一致性满足目标。

### S42. 执行灰度发布与上线验收

**前置：** S37-S41；阻断问题已关闭。

1. 发布前核验版本、迁移、配置、证书、凭证、容量余量、备份与告警，并确认回滚负责人和停止条件。
2. 按测试设备、内部用户、小批真实设备、扩大比例的顺序灰度；每批具体比例和观察窗口在发布计划中明确。
3. 每批验证 MQTT 认证与消息、命令、单向观看、多端退出、换票、双向通话、关流和异常恢复。
4. 对比成功率、延迟、首帧、异常断连、重试、资源泄漏和安全告警；达到停止条件即停止扩量或回滚。
5. 回滚时保留兼容数据库结构和审计，先控制新增操作，再处理进行中 Session/Call/任务及媒体资源。
6. 灰度稳定后完成正式验收签字，记录已接受限制和后续改进项，不将阻断问题转成无期限待办。

**交付物：** 灰度计划、逐批观察记录、回滚演练、上线验收报告。  
**验收：** 功能、安全、容量、恢复和运维均达到已确认指标，生产观察窗口内无阻断问题。

### S43. 归档交付物并完成责任移交

**前置：** S42。

1. 按下文覆盖矩阵逐项核对代码、配置、数据库迁移、API、测试和运维材料。
2. 归档生产版本、镜像摘要、固件/APP 兼容版本、参数定版依据、许可证结论与关键设计决策。
3. 明确日常运维、设备密钥轮换、媒体扩容、故障处置、任务人工重试和安全响应的责任人。
4. 将录制、多 Provider、跨地域、自研媒体等后续能力转为独立需求，不影响第一阶段验收边界。

**交付物：** 最终交付清单、版本基线、责任移交记录。  
**验收：** 接手人员可依照归档材料部署、验证、定位和恢复系统，不依赖原开发者口头说明。

**G5 检查：** S35-S43 完成，容量、安全、生产部署、恢复演练和最终移交全部验收。
