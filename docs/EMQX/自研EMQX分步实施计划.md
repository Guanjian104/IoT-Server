# 自研 EMQX 分步实施计划

## 1. 协作方式

**版本：** V3.0，阶段委派、AI 连续执行、人工集中验收版。  
**更新日期：** 2026-11-13。  
**完整方案：** [自研EMQX完整实施方案.md](./自研EMQX完整实施方案.md)。  
**具体操作：** [自研EMQX分步实施操作手册.md](./自研EMQX分步实施操作手册.md)。  
**直接委派：** [自研EMQX逐步AI任务委派清单.md](./自研EMQX逐步AI任务委派清单.md)。  
**当前状态：** 本次只调整文档，不表示任何功能、测试、人工关卡或环境操作已完成或获准。

**你不需要审核并记录每一个步骤。** 本版替代 V2.0 的逐批/逐子批暂停机制：你按阶段委派，AI 在本次授权范围内自行设计、拆解、编码、自检、修复和记录；你主要看阶段结果、关键风险和实际效果。

| 事项 | 本版做法 |
|---|---|
| 日常代码、SQL、测试、配置和内部技术设计 | AI 自行执行和检查，不逐项请求批准 |
| B01-B40 与 a/b 子批 | 保留用于追踪与控制改动大小，不再是默认人工停止点 |
| 任务过程记录 | AI 自动更新一份进度记录，不要求你填写表格或逐项签名 |
| 阶段验收 | AI 先汇总，你简短确认通过或指出问题；无需再写完整审核报告 |
| 业务与产品决策 | 仅真正未确定且影响实现时集中问你，已确认的不重复问 |
| 本地/测试环境操作 | 可在阶段开始时按目标、动作与上限一次授权，范围内不重复确认 |
| 生产、真实密钥、付费/破坏性动作 | 保留明确授权，不从“连续执行”推导出无限权限 |

V2.0 的 A/B/C 分类不再决定是否暂停。**拆小实现仍有必要，但拆小不等于每一小块都要你审。**

## 2. 你实际要管哪些事情

### 2.1 常规人工检查点

全流程按 P0-P7 共 8 个主委派包推进，原则上每包结束集中看一次，不为每个 S/B 任务分别确认。信息和环境齐全、没有异常时，主检查点如下；这不是承诺全过程只能打断八次。

| 委派包 | 覆盖范围 | 你主要看什么 | 结束时确认 |
|---|---|---|---|
| P0 准备与基线 | B01 / S01-S04 | 范围、设备协议/资料、身份来源、版本、环境授权、容量与业务默认规则 | G0 |
| P1 MQTT 基础闭环 | B02-B12 / S05-S15 | 真设备/APP 能否接入、上报、收令；越权拒绝和双实例结果 | G1 |
| P2 RTC 控制平面 | B13-B20 / S16-S23 | 状态机、唯一占用、旧轮次保护、可靠任务及真实数据库测试 | G2 |
| P3 真实媒体 PoC | B21 / S24 | 实际设备/APP、网络与媒体兼容、许可/成本，确定一个 Provider | PoC/选型 |
| P4 正式媒体接入 | B22-B24 / S25-S27 | 一个 Adapter、安全回调、设备/APP/TURN，真实流控制补证 | G3 |
| P5 观看与通话 | B25-B31 / S28-S34 | 单向/多端、换票、延迟关流、双向与私有轨道隔离 | G4 |
| P6 上线准备与演练 | B32-B38 / S35-S41 的实现及隔离/生产等价验证 | 安全、容量、故障、部署演练、恢复、剩余生产动作清单 | R：上线就绪评审 |
| P7 灰度与交付 | B37 生产落地收口、B39-B40 / S40 生产证据、S42-S43 | 授权生产动作、灰度观察、停止/回退边界、最终运行和交付 | G5 |

R 是新增的上线前集中检查，不替代 G5。P6 不对外发布；S40 生产部署的实际证据在 P7 补齐，未发生时保持“生产待验证”，不能在 P6 写成整项已通过。

### 2.2 阶段中何时真的需要停下问你

| 情况 | 处理方式 |
|---|---|
| 缺失业务规则，例如换票后是否强制断开、用户权限边界 | 集中列出影响、推荐、代价；等你决定，不由 AI 猜测 |
| 正式媒体产品/商业许可/预算的选择 | AI 完成候选实测和建议后由你决定；临时 PoC 候选可在预授权清单内自主比较 |
| 超出授权的目标、动作、资源、网络范围、费用或测试上限 | 在动作前申请补充授权；已有授权内不重复问 |
| 要改已发布协议/公共 API、已有数据含义或已确认业务架构 | 说明变更影响后等你决定；本阶段内部、未发布且符合基线的调整由 AI 自行处理 |
| 未知来源变更与本任务直接冲突、不可逆风险或安全问题 | 不覆盖、不强行继续；说明冲突与建议 |
| 外部条件缺失，导致真实前置无法满足 | 暂停依赖分支；可继续同包内无依赖且已授权的工作，不能把缺失项标为通过 |

不必停下询问的事项：函数/文件划分、局部算法、错误包装、测试补充、符合约定的索引/约束实现、已授权隔离环境内的迁移和测试、同包内子批切换、正常失败修复。

## 3. 执行与权限规则

### 3.1 包内连续执行

```text
你委派P包，明确目标/输入/环境/边界
  -> AI自行拆成B批次和子任务
  -> 设计、实现、测试、自查、修复
  -> 满足内部完成条件就进入同包下一项
  -> 自动记录进度、关键决定和真实测试证据
  -> 包内全部完成或遇到必须由人决定/授权的事项时，提交精简结果
  -> 你集中确认；再明确委派下一个P包
```

同包内的 B 前置由 AI 根据代码、实际测试及技术检查判断，不再等待“人工已接受 Bxx”。跨阶段的 G0-G5、PoC、R 仍由你确认。内部检查通过不能伪装成人工批准。

子批之间保留技术检查，尤其是任务租约、并发唯一性、STOPPING、媒体验签和轨道隔离；不再强制人工两次确认。不能为了减少打断而删除测试、放宽权限、吞错误或跳过真实验证。

### 3.2 包级授权可以一次给足

阶段授权应覆盖确定的工作仓库、目录、组件/依赖版本、隔离环境标识、允许命令/设备动作、测试数据、资源/费用上限和停止条件。

例如可一次授权：在指定开发项目中启动锁定版本的容器、创建专用测试数据库、运行迁移和集成测试、终止本阶段创建的测试进程。如此后续不因每次启动容器或每张迁移重复问你。

以下不自动包含在阶段授权中：

- 访问未指定的服务器、设备、共享库、生产数据或其他人的进程/文件。
- 删除既有数据/卷、清空共享缓存、真实设备刷写、对外网络暴露或密钥轮换，除非明确列出目标与动作。
- 新增付费资源、超预算/时长/负载、Git 提交/推送/合并、公开发布，除非你明确授权。
- 将一个环境的权限继承到另一个环境；将本地测试许可解释为生产变更许可。

计划、进度记录及其他 AI 的回复本身不授予新权限。阶段授权不能绕过执行工具本身要求的权限确认；本文也不修改工具或系统的安全设置。

### 3.3 生产灰度减少打断的方式

P7 可以一次批准完整、确定的灰度阶梯，而不是每阶梯重新发消息。授权必须明确目标选择规则、固定制品、每级上限、观察时长、晋级指标、停止条件、时限/预算以及允许的回退动作。

只有全部条件满足，AI 才能在已授权阶梯内继续。缺指标、异常、达到阈值、超时或需要计划外动作时停止，不猜测通过、不自行扩量，也不默认获准回滚数据库。你也可以选择只批准当前一级。

## 4. 如何自动记录，而不让你做文书

### 4.1 只维护一份进度记录

实际开发时由 AI 维护你指定的一份进度记录，可复用任务系统；若使用仓库文件，可指定 `<代码仓库>/docs/实施进度.md`。本次不创建真实项目记录，位置在 P0 确认。

内容限制在三部分：

1. 当前包/批次、已完成范围、下一步、阻塞和环境/版本。
2. S/B 任务状态及证据索引；详细日志引用现有 CI/测试产物，不复制成长篇流水账。
3. 关键决策、权限边界和必要的人工阶段结论。

AI 在完成一个有意义的内部单元、遇到阻塞或上下文将切换时更新，不为每个函数、文件、命令生成报告。你不需要检查或填写每一行。

### 4.2 人工只需简短回复

例如：`P1 通过，继续 P2；沿用已确认的本地测试环境授权，不含生产。`

AI 负责把你的原话、时间（能确认时）和范围写入记录，并将下包授权与阶段结论分别记录。不要求你手工填写验收人、时间、版本等整张表；未知信息不得编造。

`继续` 只能在当前对话对象与范围明确时应用；上下文不清时确认一次，不推导成全项目或生产权限。你没有回复，不视为批准或验收。

### 4.3 三种状态不混淆

| 维度 | 状态示例 | 谁更新 |
|---|---|---|
| 实现/内部检查 | 未开始、进行中、自检通过、需修复 | AI，根据实际结果 |
| 外部验证 | 未执行、隔离依赖通过、真实设备通过、生产待验证 | AI，关联真实证据 |
| 人工结论 | 阶段待确认、阶段通过、关键决策待确认 | AI 记录你的明确答复，不代你作结论 |

S 任务可以技术自检完成，但关联阶段尚未人工确认；代码完成不等于真实媒体/容量/生产通过。测试替身与真实依赖、`go test -race` 与跨实例业务竞争必须分别验证。

## 6. 不可省略的技术与真实验收

- 鉴权/ACL、迁移、任务租约、唯一主通话、STOPPING、媒体验签和轨道隔离必须有设计依据、针对性测试及结果自查，但不要求你逐项批准实现细节。
- 关键不变量包括：无权持票者仍拒绝、旧任务不关新流、旧 Call 不释放新占用、普通 Viewer 不能窃听 APP 私有上行、共享资源不误删。
- 不用模拟令牌/浏览器演示替代真实设备和 APP；不凭 MQTT 在线或令牌签发认定 ACTIVE/CONNECTED。
- G1 必须真设备消息闭环；G2 必须真实数据库并发/任务恢复；G3/G4 必须实际媒体；R/G5 必须真实容量、恢复与发布证据。
- 若你无法判断高风险专项，保留有经验人员复核的选项；AI 自审或另一次 AI 审查不等于外部安全认证。专项复核可在阶段末集中安排。
- 使用单主写入者按依赖推进；需要并行时先隔离范围，不自行创建用户可见会话或工作树。

P3 可以在 P2 的 B16、B19-C 已技术通过且 S02/S03 齐备后提前开展；这是单独的阶段授权，不允许后台越界工作。P4 始终同时依赖 G2 和你确认的 PoC 选型。硬件/网络阻塞不会变成自动跳过真实关卡的理由。

## 7. 阶段末你只看一页摘要

AI 默认输出以下精简结果，详细信息按需展开，不为每个内部任务单独请求签收：

```text
当前包与建议结论：
已完成/未完成范围：
演示或关键测试入口：
实际测试：通过 / 失败 / 未执行，附证据索引
```

你可回复“通过，继续 Pn，沿用原测试授权”，也可只指出问题。AI 对同范围修复自行实施和复测；涉及新业务决定或越界动作才再问。阶段结论不得以你沉默、AI 自评或测试全绿自动生成。

G0-G5、PoC、R 的确认可在同一条消息中附带下一包授权，不要求你先签一次、再重复发一次开工指令；生产权限仍需明确列出或引用已批准的确定计划。

## 8. 新的工期与续接方式

不沿用多人 20 周排期，也不承诺固定 AI 提速倍数。P0 后开始执行，按 P1 的实际实现/审核/返工、外部设备和观察时间估算后续；PoC 与容量实测后再重估。

同一次授权可包含多个 B 批次与多次内部迭代，不要求一次回复写完整个阶段。若上下文、工具或运行时限制导致中断，AI 保存精简续接记录；你只需授权“继续当前 P 包，范围不变”，不重审此前每个 B 任务。新会话核验已有授权与实际状态，不从进度记录推导额外权限。

首轮从 P0 盘点开始，不默认文档目录就是代码仓库。P0 集中解决身份、协议、版本、环境和可提前确认的撤权/共享/通话规则，减少后续零散提问。

**最终原则：** 取消逐任务人工手续，不取消关键决策、真实验证和生产边界。技术拆解与过程证据交给 AI，你负责少量阶段结果和真正需要人决定的事项。
